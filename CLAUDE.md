# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CDP4-COMET WebServices is the Starion Group concurrent-design REST API, the reference implementation of **ECSS-E-TM-10-25 Annex A (the UML "master model") and Annex C (the REST API)**. It is a .NET 9 ASP.NET Core service backed by PostgreSQL (9.6+, **16.x preferred**), using [Carter](https://github.com/CarterCommunity/Carter) for routing on top of ASP.NET, Autofac for DI (primarily **property injection**, hence the `PropertiesAutowired` calls everywhere), and Hangfire for background work. Behavioural correctness is verified against the external [ecss-10-25-annexc-integration-tests](https://github.com/STARIONGROUP/ecss-10-25-annexc-integration-tests) suite — keep that suite in mind when changing protocol-visible behaviour.

Domain DTOs, serializers, metadata, and the messaging library all come from the [COMET-SDK](https://github.com/STARIONGROUP/COMET-SDK-Community-Edition) (`CDP4Common`, `CDP4JsonSerializer`, `CDP4MessagePackSerializer`, `CDP4DalCommon`, `CDP4ServicesMessaging`). When the data model needs to change, that change happens in the SDK first; the autogen layer here is regenerated from the SDK metadata.

## Common commands

Build / test / run from the repo root (PowerShell or bash):

```bash
dotnet restore COMET-WebServices.sln
dotnet build   COMET-WebServices.sln -c Debug
dotnet test    COMET-WebServices.sln                                # all unit tests
dotnet test    CometServer.Tests/CometServer.Tests.csproj           # one project
dotnet test    CometServer.Tests/CometServer.Tests.csproj --filter "FullyQualifiedName~OperationProcessorTestFixture"  # one fixture
dotnet run --project CometServer/CometServer.csproj                 # start API on http://localhost:5000
```

Tests use **NUnit + Moq**. There are five test projects mirroring the production projects: `CDP4Authentication.Tests`, `CDP4Orm.Tests`, `CDP4WspDatabaseAuthentication.Tests`, `CometServer.Tests`, plus the integration suite that lives in a separate repo.

The API needs PostgreSQL. Bring up just the DB (and RabbitMQ) for local dev with `compose.bat dev` (Windows) or `docker compose -f docker-compose-dev.yml up`. `compose.bat` is the convenience launcher — `dev`, `devtest`, `up`, `rebuild`, `nginx` etc. are all defined there. CI uses `stariongroup/cdp4-test-database-community-edition:4.2.0` as the DB image (see `.github/workflows/CodeQuality.yml`).

Docker images:
- `./docker-build-local.sh` — local image (Linux shell; works in Git Bash).
- `./docker-build-attested.sh` — pushes attested image with SBOM to Docker Hub.

Running the integration tests locally: start the API, then `POST` the `Data.zip` exchange file from the integration-test repo to `http://localhost:5000/Data/Exchange`, then run that repo's test solution. The CI workflow shows the exact sequence.

## Solution layout

Eight projects make up the solution:

| Project | Purpose |
| --- | --- |
| `CometServer` | The web host. Carter modules under `Modules/`, DI/Autofac wiring in `Startup.cs`, entry point in `Program.cs`, business + protocol services under `Services/`. |
| `CDP4Orm` | PostgreSQL data-access layer. DAOs, transaction manager, revision tracking, migration engine, raw SQL schema/triggers. |

| `CDP4DatabaseAuthentication` | First-party plugin: authenticates against the COMET DB. |

| `*.Tests` | NUnit test projects (one per production project, except `CDP4DatabaseAuthentication`). |

## Architecture you need to know

### The auto-generated layer (do not edit by hand)

A large fraction of the codebase is generated from the ECSS-E-TM-10-25 Annex A UML model. **These directories are regenerated by external tooling — edit them only as a deliberate choice; normal feature work goes in the hand-written extension classes that sit alongside them:**

- `CometServer/AutoGenServices/` (~360 files) — one `ThingNameService` per 10-25 class.
- `CDP4Orm/AutoGenDao/` — one `ThingNameDao` per class.
- `CDP4Orm/AutoGenStructure/*.sql` — schema, triggers, and indexes for `SiteDirectory` and `EngineeringModel` partitions.
- `CDP4Orm/AutoGenOrmHelpers/DaoResolver.cs`.

All autogen classes are emitted as **`partial`**, so the way to extend them without touching the generated file is:

- For a `Thing`'s **business rules / cross-cutting validation** (cycle detection, default values, propagation): add an `IOperationSideEffect` implementation under `CometServer/Services/Operations/SideEffects/Implementation/` (~50 exist). `OperationSideEffectProcessor` discovers them via Autofac and fires them before/after each create/update/delete in `OperationProcessor`.
- For **DAO-layer hooks** (extra SQL or in-DB validation that has to share the same Npgsql transaction): add a partial `XxxDao` file under `CDP4Orm/Dao/Supplemental/` and override `BaseDao.BeforeWrite/AfterWrite/BeforeUpdate/AfterUpdate/BeforeDelete/AfterDelete`. Each generated `Write/Update/Delete` already calls these via the `isHandled`/value pattern.

**Acyclic validation** for the data graph (BooleanExpression term loops, ElementDefinition self-containment, ParameterGroup loops, Category supercategory loops, RDL `requiredRdl` chains, etc.) lives entirely in side effects and throws `AcyclicValidationException` — see `Cyclic-Cycles` in the repo wiki for the full table.

### Request flow

```
Carter module (Modules/10-25/*Api.cs)
  → ApiBase helpers (auth, request-token, content negotiation, MessagePack vs JSON)
  → IServiceProvider (Services/) resolves the right ThingNameService for a route segment
  → Service performs IPermissionService check + delegates to a Dao
  → Dao executes parameterised SQL via Cdp4TransactionManager
  → Side-effects fire before/after persistence
  → Response is serialized through Cdp4DalJsonSerializer or MessagePackSerializer
```

The two main API surfaces are `SiteDirectoryApi` (the global directory of models, persons, RDLs) and `EngineeringModelApi` (per-model and per-iteration data). `ExchangeFileImportApi` / `ExchangeFileExportApi` handle the JSON exchange file format used to seed/migrate data.

`OperationProcessor` (`Services/Operations/`) is the heart of write handling. It receives a `CDP4DalCommon.Protocol.Operations.CdpPostOperation`, resolves containment, runs validation/permissions, persists in dependency order, and lets `OperationSideEffectProcessor` hook in around each operation.

### Persistence model

A PostgreSQL cluster hosting CDP4-COMET has **three databases**:

- `cdp4server` — the live data. Configured by `Backtier:Database`.
- `cdp4serverrestore` — a snapshot loaded from an Annex C.3 zip via `POST /Data/Exchange`. `GET /Data/Restore` rolls `cdp4server` back to this snapshot. Gated by `Backtier:IsDbSeedEnabled` / `IsDbRestoreEnabled` (set both to `false` in production).
- `cdp4manage` — bootstrap database, only used to prove the cluster is provisioned correctly.

Inside `cdp4server` there are three kinds of **schema** (= "partition" throughout the C# code):

- `SiteDirectory` — exactly one. Global directory of persons, models, RDLs, organizations.
- `EngineeringModel_<EngineeringModel.Iid>` — one per model.
- `Iteration_<EngineeringModel.Iid>` — one per model (not per iteration). All iterations of a model share this schema; rows are scoped by validity.

For every concrete and **abstract** 10-25 class, multiple tables exist within the relevant schema. Knowing this family is essential to read the autogen DAO SQL:

| Table | Holds |
| --- | --- |
| `[Thing]` | Current state. `Iid`, `ValueTypeDictionary` (HSTORE for value props), `ValidFrom`/`ValidTo`, plus columns for properties defined at this level of the inheritance tree. References go in cross tables. |
| `[Generalization]` | One table per inheritance level (e.g. `Thing`, `DefinedThing`, `ElementBase`, `ElementDefinition`). A property column lives at the level where the property is declared in 10-25; child tables don't redefine it. Writes/updates/deletes cascade up to `ThingDao` via `base.Write(...)` chains. |
| `[Thing]_Audit` | Append-only history written by triggers `process_timetravel_before/after`. Drives time-travel reads. |
| `[Thing]_Revision` | One row per revision with the full Jsonb. Used by revision-aware GETs (`?revisionNumber=`, `?revisionFrom=`, `?revisionTo=`). Populated by `RevisionService`. |
| `[Thing]_Cache` | Latest Jsonb only — fast path. The `isCachedDtoReadEnabledAndInstant` flag on `Dao.Read(...)` selects this table, otherwise the read goes through `[Thing]_View`. Only normal (non-abstract) tables have a `_Cache`. |
| `[Thing]_View` | View that reconstructs a Thing by joining its row with all generalization and cross tables. Default read path when not reading from cache. |
| `A_B` cross tables | Many-to-many references (e.g. `ElementDefinition_ReferencedElement`). Also have `_Audit` counterparts. |

**Audit & revision are driven by per-transaction state**, not by C# wrapping each statement. `Cdp4TransactionManager` (the only place that opens an `NpgsqlTransaction`) creates a temporary `transaction_info` table at the start of the transaction with `audit_enabled`, `session_user`, `session_instant`, `transaction_time`, `period_start`. SQL functions (`get_audit_enabled()`, `get_current_revision()`, `get_session_*()`, `get_transaction_time()`, `[Thing]_Data()`) and the `[Thing]_audit_prepare` / `[Thing]_audit_log` / `[Thing]_apply_revision` / `[Thing]_thing_delete_trigger` triggers all read this table. The temp table dies with the transaction. **Don't open raw `NpgsqlTransaction` objects — go through `Cdp4TransactionManager` or you lose audit/revision behaviour.**

Per-partition `RevisionRegistry` issues monotonically increasing revision numbers (one sequence per `SiteDirectory`, one per `EngineeringModel_<iid>`). `RevisionService` writes the `_Revision` and `_Cache` rows; `RevisionResolver` materializes historical reads.

### DAO interface surface

Each generated `IXxxDao` (concrete classes only) exposes exactly this set of methods — the protocol's `_create`/`_update`/`_delete` plus ordered-collection mutations map onto them:

```csharp
IEnumerable<Xxx> Read(NpgsqlTransaction, string partition, IEnumerable<Guid> ids = null, bool isCachedDtoReadEnabledAndInstant = false);
bool Write       (NpgsqlTransaction, string partition, Xxx dto, Thing container = null);
bool Update      (NpgsqlTransaction, string partition, Xxx dto, Thing container = null);
bool Delete      (NpgsqlTransaction, string partition, Guid iid);
bool ReorderCollectionProperty   (NpgsqlTransaction, string partition, string propertyName, Guid iid, OrderedItem orderUpdate);
bool AddToCollectionProperty     (NpgsqlTransaction, string partition, string propertyName, Guid iid, object value);
bool DeleteFromCollectionProperty(NpgsqlTransaction, string partition, string propertyName, Guid iid, object value);
```

`partition` is the schema name (`"SiteDirectory"`, `"EngineeringModel_<iid>"`, `"Iteration_<iid>"`). The DTO/recordset mapping is hand-written (`MapToDto`) — no Dapper / EF / reflection — for performance and because the schema is generated alongside the DTOs.

### Authentication

`Startup.SetUpAuthentication` reads `Authentication:Basic|LocalJwtBearer|ExternalJwtBearer:IsEnabled` from `appsettings.*.json`. Exactly one of {Basic+LocalJwt} or {ExternalJwt} can be active. `External` mode requires the closed-source `CDP4ExternalJwtAuthentication` plugin (Enterprise Edition); the Community build will refuse to start without it.

`AuthenticationPluginInjector` discovers DLLs at runtime by scanning the `Authentication/` folder next to the binary (e.g. `Authentication/CDP4Database/CDP4DatabaseAuthentication.dll`). The plugin DLLs and their `config.json` are copied there by the `CopyAuthenticationPlugins` MSBuild target in `CometServer.csproj` and again by the `Dockerfile`. If you are touching plugin loading or auth, mirror changes in **both** the MSBuild target and the Dockerfile.

### Migrations

Database migrations live in `CDP4Orm/MigrationScript/*.sql`. Filename convention is **load-bearing** — `MigrationService` parses it:

```
{Partition}_{OnStartUpOnly?}_{yyyyMMdd}_{Major}_{Minor}_{Revision}_{Sequence}_{Description}.sql
{Partition} = All | SiteDirectory | EngineeringModel | Iteration | <ThingTableMigrationTemplate variants>
```

Templates whose name contains `NonThingTableMigrationTemplate` or `ThingAuditTableMigrationTemplate` are applied to every matching table at startup; the templating is driven by `NonThingTableMigration.cs` / `ThingAuditTableMigration.cs`. When adding a migration, copy the naming exactly and add the corresponding C# subclass only if you need non-template behaviour.

### Long-running tasks

POSTs to `/SiteDirectory/{iid}` and `/EngineeringModel/{iid}/iteration/{iid}` can spill into the background. The client passes `?waitTime=` (seconds) on the POST; if the operation hasn't finished by then, the response becomes a `Task` JSON object (`statusKind: PROCESSING`, etc.) and the work continues under Hangfire. The client polls `/tasks/{id}` (or `POST /tasks/{id}` to cancel). `CometTaskService` is the registry. `LongRunningTasks:RetentionTime` controls how long completed tasks stay queryable.

### Cherry-pick

`Services/CherryPick/` implements server-side filtered iteration reads (subset of categories/parameter types). Touching iteration read paths usually means touching `CherryPickService` and `ContainmentService` too.

### HTTP protocol shape (Annex C.2)

Useful to keep in mind when writing or reviewing modules:

- **Only `GET` and `POST`** are supported. No PUT/PATCH/DELETE — mutations go in a POST body with `_create` / `_update` / `_delete` (and the CDP4 extension `_copy`) parts. Whole-object create needs every mandatory property; updates can be sparse but must include `iid` + `classKind`.
- POST is **only valid on two routes**: `/SiteDirectory/{iid}` and `/EngineeringModel/{iid}/iteration/{iid}`. Mutating things owned by an `EngineeringModel` but not by an `Iteration` still goes through an Iteration POST. There is **no** POST to `/EngineeringModel/{iid}` — this is a frequent client-side bug.
- Content negotiation: `Accept: application/json` or `application/msgpack` (binary, identical schema, faster). If both are sent, MessagePack wins.
- CDP4 extension headers: `Accept-CDP` opts the client into CDP4-COMET extensions on top of pure 10-25; `CDP4-Token` is a correlation id echoed into logs. Responses always carry `CDP4-Server`, `CDP4-Common`, and `Content-Type: application/json; ecss-e-tm-10-25; version=1.0.0`.
- GET query params: `extent=shallow|deep`, `includeReferenceData`, `includeAllContainers`, `includeFileData`, plus the revision family `revisionNumber=N` / `revisionFrom` / `revisionTo`. **`revisionNumber` must be the only query param** — don't combine it with the others. `revisionNumber=0` is equivalent to `extent=deep`.
- Out-of-band routes worth knowing: `/` (welcome page), `/healthz`, `/health/startup`, `/ready`, `/username`, `/auth/schemes`, `/login` + `/refresh` (only when `LocalJwtBearer` is enabled), `/Data/Exchange` (Annex C.3 seed), `/Data/Restore`, `/tasks` + `/tasks/{id}`, `/hangfire` (dashboard).

### Configuration

Real config lives in `appsettings.Development.json` and `appsettings.Production.json` (the top-level `appsettings.json` is intentionally empty). At Docker runtime, **any setting can be overridden by an env var** with double-underscore notation:

```yaml
environment:
  - Kestrel__Endpoints__Http__Url=http://0.0.0.0:5001
  - Backtier__HostName=cdp4-postgresql
  - Authentication__Basic__IsEnabled=true
```

Config sections of note: `Kestrel`, `Midtier` (upload/storage/export dirs, `BacktierWaitTime`), `Backtier` (DB connection, `IsDbSeed/Restore/ImportEnabled` — disable in production), `MessageBroker` (RabbitMQ on/off), `EmailService`, `Defaults:PersonPassword` (default password assigned to all persons seeded from C.3), `Changelog` (`CollectChanges`, `AllowEmailNotification`), `Authentication` (see above), `Health:RequireHost`, `LongRunningTasks:RetentionTime`, `Serilog`. Plugins (e.g. `CDP4Database`) carry their own `config.json` next to their DLL — that's where rank/enabled flags for individual auth connectors live.

## Conventions

From `.github/CONTRIBUTING.md` and `COMET-WebServices.sln.DotSettings`:

- 4-space indent, no tabs, no underscore prefix on members, **always** `this.` for instance members.
- `using` directives **inside** the namespace block.
- Brace every block, even one-liners.
- No `#region`s. Ever.
- Use `var`, C# type aliases (`int`, `string`).
- Long descriptive names — no Hungarian, no abbreviations.
- Branch from `development`, PR back to `development`. Never PR from `master`/`development` directly.

## Things that surprise people

- **Namespace `using` placement**: ReSharper will fight you if you put `using` outside the namespace. Match the existing style.
- **Generated services are not edited**: changes to `AutoGenServices/*.cs` will be lost. Add side-effects or supplemental services instead.
- **Two ConfigureContainer paths**: `Startup.ConfigureServices` registers framework + auth services into MS DI; `Startup.ConfigureContainer` registers everything else into Autofac and **overrides** anything from the first method. New domain services almost always go in `ConfigureContainer`.
- **Carter module discovery is reflection-based** (`Startup.cs` line ~439): any public class extending `CarterModule` in the `CometServer` assembly is auto-registered.
- **`appsettings.json` is intentionally empty** — real config lives in `appsettings.Development.json` and `appsettings.Production.json`. The Dockerfile renames `Production` to `appsettings.json` at image-build time.
- **`OperationProcessor`** has been the bug locus historically. When you change it, also expand `OperationProcessorTestFixture` and run the external integration suite — unit tests alone do not catch protocol regressions.
- **Plugin auth folder copy is duplicated** in `CometServer.csproj` (`CopyAuthenticationPlugins` target) and `Dockerfile` (`COPY --from=build-env`). Keep them in sync.
- **Default seeded credentials** are `admin` / `pass`. If you've lost the local admin password, the wiki's `Restore-default-admin-password` page has the exact UPDATE statements against `Person`, `Person_Cache`, and `Person_Revision` to reset it (you must update all three because reads can come from cache or from a historical revision row).
- **`Cdp4TransactionManager.SetupTransaction`** is what makes time-travel work — bypassing it (raw `connection.BeginTransaction()`) gives you a transaction with no `transaction_info` row, which means audit triggers behave as if `audit_enabled=false` and `RevisionRegistry` allocation may fail.
